2. What is a Python Module?
A module is simply a Python file containing code that you want to reuse.
Suppose:
project/
│
├── main.py
└── calculator.py
calculator.py
def add(a, b):    return a + bdef subtract(a, b):    return a - b
main.py
import calculatorprint(calculator.add(10, 20))print(calculator.subtract(20, 5))
Output:
30
15
That's the basic idea of a module.

3. Why Modules Exist
Imagine putting everything inside:
main.py
You eventually get:
5000 lines
100 functions
50 classes
database code
API code
logging
validation
ETL logic
That's a disaster.
Instead:
main.py
database.py
api.py
validation.py
logging_config.py
transformations.py
Each file has a responsibility.
This is especially important in Data Engineering.

4. Different Ways to Import
Method 1 — import module
import calculatorcalculator.add(10, 20)

Method 2 — import specific function
from calculator import addprint(add(10, 20))
You don't need:
calculator.add()

Method 3 — multiple imports
from calculator import add, subtract

Method 4 — alias
import calculator as calcprint(calc.add(10, 20))
You'll see this constantly in Data Engineering.
For example:
import pandas as pdimport numpy as np
Here:
pandas → pd
numpy  → np

5. from module import *
You can technically do:
from calculator import *
Then:
print(add(10, 20))
But don't do this in professional code.
Why?
Because you lose clarity.
For example:
from module1 import *from module2 import *
Both might contain:
process()
Now:
process()
Which one?
Bad practice.

6. __name__ == "__main__"
This is extremely important.
Consider:
# calculator.pydef add(a, b):    return a + bprint("Calculator loaded")
If you do:
import calculator
the print executes.
That's because Python executes the module during import.
Instead:
def add(a, b):    return a + bif __name__ == "__main__":    print(add(10, 20))
Now:
python calculator.py
runs:
30
But:
import calculator
doesn't execute the test code.
Why?
When executed directly:
__name__ == "__main__"
When imported:
__name__ == "calculator"
This pattern is extremely common.

7. What Happens Internally During Import?
When you write:
import calculator
Python roughly does:
1. Search for calculator
        ↓
2. Find calculator.py
        ↓
3. Load module
        ↓
4. Execute module code
        ↓
5. Create module object
        ↓
6. Store it in sys.modules
That's why repeated imports don't normally execute the module again.
Example:
import calculatorimport calculatorimport calculator
Python caches imported modules in:
sys.modules
You can see it:
import sysprint(sys.modules)

8. Python Search Path
This is directly related to the error you recently encountered:
ModuleNotFoundError: No module named 'student'
Python searches certain locations when you import.
You can see them:
import sysprint(sys.path)
Example:
[
    '/home/user/project',
    '/usr/lib/python...',
    ...
]
Python looks through these locations to find your module.

9. Your Previous Error Explained
You had something similar to:
Python/

│   └── Static_method/
│       └── static_method.py
│

10. What is a Package?
A package is a directory used to organize modules.
Example:
data_pipeline/
│
├── main.py
│
└── database/
    ├── __init__.py
    ├── mysql.py
    └── postgres.py
Here:
database
is the package.
And:
mysql.py
postgres.py
are modules.

11. __init__.py
Traditionally:
database/
├── __init__.py
├── mysql.py
└── postgres.py
__init__.py tells Python that the directory is intended to behave as a package.
Modern Python also supports namespace packages without __init__.py, but for learning and many normal application structures, understanding __init__.py is essential.

12. Package Import
Suppose:
database/
├── __init__.py
├── mysql.py
└── postgres.py
mysql.py
def connect():    print("Connecting to MySQL")
main.py
from database.mysql import connectconnect()
Output:
Connecting to MySQL
Or:
import database.mysqldatabase.mysql.connect()

13. __init__.py Can Contain Code
Example:
# database/__init__.pyprint("Database package loaded")
Then:
import database
can execute that initialization code.
But don't stuff random logic into __init__.py.
Keep it lightweight.

15. Absolute Imports
Suppose:
project/
├── main.py
└── utils/
    ├── __init__.py
    └── validation.py
Use:
from utils.validation import validate_email
This is an absolute import.
It starts from the project's import root.

16. Relative Imports
Inside packages, you can use:
from .validation import validate_email
. means:
current package
Two dots:
from ..utils import helper
means:
parent package
Example:
project/
│
└── pipeline/
    ├── __init__.py
    ├── utils/
    │   ├── __init__.py
    │   └── validation.py
    │
    └── jobs/
        ├── __init__.py
        └── daily.py
Inside:
daily.py
you could use:
from ..utils.validation import validate

17. Absolute vs Relative Imports
Generally:
Application code
Prefer clear absolute imports:
from pipeline.utils.validation import validate
Package internals
Relative imports can be useful:
from .validation import validate
Don't blindly use relative imports everywhere.

20. Module vs Package vs Library
This distinction confuses beginners.
Suppose you install:
pip install pandas
You use:
import pandas
pandas is a package/library providing many modules and functionality.
Think:
Module
   ↓
One Python file

Package
   ↓
Collection/namespace of Python modules

Library
   ↓
Reusable functionality intended for applications
These terms overlap in casual usage, so don't obsess over terminology.

23. Virtual Environment
This is one of the most important Python concepts for professional development.
Don't install everything globally.
Create:
python -m venv .venv
Activate on Linux:
source .venv/bin/activate
Then:
pip install pandas
Now your project has its own environment.

24. Why Virtual Environments Matter
Suppose:
Project A
pandas 2.x

Project B
pandas 1.x
If you install globally:
System Python
    ↓
pandas 2.x
Project B may break.
With virtual environments:
Project A
└── .venv
    └── pandas 2.x

Project B
└── .venv
    └── pandas 1.x
Much safer.

25. pyproject.toml
Modern Python projects often use:
pyproject.toml
instead of relying solely on:
requirements.txt
For example:
[project]
name = "data-pipeline"
version = "1.0.0"
dependencies = [
    "pandas",
    "sqlalchemy",
    "requests"
]
Tools such as Poetry, Hatch, uv and modern packaging workflows use pyproject.toml.
You should learn it after you've understood normal modules/packages.

41. Circular Imports
This is an important advanced problem.
Suppose:
a.py
from b import function_b
And:
b.py
from a import function_a
You get:
a → b
↑   ↓
└───┘
This is a circular dependency.
It can cause:
ImportError
partially initialized module
Bad architecture
database.py
    ↓
service.py
    ↓
database.py
You should redesign the dependency structure rather than patching the import.

42. __all__
You can control what a module exposes with:
__all__ = [
    "add",
    "subtract"
]
Example:
from calculator import *
will use __all__ to determine exported names.
It's not something you need every day, but it's useful when designing packages.

43. Dynamic Imports
Python allows:
import importlib

module = importlib.import_module("math")

print(module.sqrt(25))
This is a dynamic import.
Useful when:
plugin systems
optional dependencies
configuration-based loading
frameworks
But don't use dynamic imports just because they look advanced.

44. __pycache__ and .pyc
When Python imports a module, it can generate compiled bytecode:
__pycache__/
    calculator.cpython-*.pyc
Don't manually manage these.
Add:
__pycache__/
*.pyc
to .gitignore.

45. Important Import Rules
Memorize these:
Rule 1
Python imports names, not arbitrary files from anywhere.
import module
requires Python to find module through its import system.

Rule 2
Don't depend on random working directories.
This causes many:
ModuleNotFoundError
issues.

Rule 3
Don't solve every import problem with:
sys.path.append(...)
This is often a band-aid.

Rule 4
Use a proper project/package structure.

Rule 5
Avoid:
from module import *
in professional code.

Rule 6
Avoid circular dependencies.

Rule 7
Use virtual environments.

Rule 8
Pin/manage dependencies for reproducible deployments.

Rule 9
Don't put secrets inside modules.
Bad:
PASSWORD = "myPassword123"
Better:
import osPASSWORD = os.getenv("DB_PASSWORD")
Or use a proper secret-management system.

Suppose tumhare laptop me Python installed hai:

4. Type Hints kya hain?
Python dynamically typed language hai.
Tum likh sakte ho:
def add(a, b):    return a + b
Python ko pehle se nahi bataya ki:
a → int
b → int
Type hint ke saath:
def add(a: int, b: int) -> int:    return a + b
Meaning:
a should be int
b should be int
return value should be int

Important point
Type hints normally runtime par Python ko force nahi karte.
Ye:
def add(a: int, b: int) -> int:    return a + b
ka matlab ye nahi hai ki Python automatically har call ko reject karega:
add("10", "20")
Python generally runtime type enforcement nahi karta.
Type hints mainly help:
developer
IDE
static type checkers
documentation
maintainability

5. Type Hints ke examples
Variable
name: str = "Kanha"age: int = 21salary: float = 25000.50is_active: bool = True

List
numbers: list[int] = [1, 2, 3, 4]
Meaning:
numbers → list
elements → int

Dictionary
users: dict[int, str] = {    1: "Kanha",    2: "Rahul"}
Meaning:
key → int
value → str

Function
def calculate_salary(    salary: float,    bonus: float) -> float:    return salary + bonus

6. Optional values
Suppose:
name = None
Type hint:
name: str | None = None
Meaning:
name can be:
str
OR
None

8. Dataclass kya hai?

Assert : 
assert ka main purpose program ke andar apni assumptions ko check karna hai. Ye normal input validation ke liye nahi bana.
Ek simple situation dekho

Tum function bana rahe ho:

def calculate_average(total, count):    
return total / count

Tumhare function ki ek assumption hai:
count kabhi 0 nahi hona chahiye.

Tum ye assumption explicitly likh sakte ho:
def calculate_average(total, count): 
   assert count > 0, "count should be greater than 0"    return total / count

Ab agar kisi bug ki wajah se:
calculate_average(100, 0)

ho gaya, Python immediately bolega:
AssertionError: count should be greater than 0

Toh fayda kya hua?
Without assert:

Bug
 ↓
function
 ↓
division by zero
 ↓
error somewhere else
With assert:
Bug
 ↓
assumption check
 ↓
AssertionError
 ↓
problem immediately identify

Real-life analogy
Suppose tum Data Engineer ho aur tumhari pipeline me ye rule hai:
"Transformation stage tak data aane ke baad customer_id column definitely exist karega."

Tum likh sakte ho:
assert "customer_id" in df.columns

Agar kisi previous step ne galti se column hata diya:
Extract
   ↓
Transform
   ↓
customer_id missing ❌
   ↓
ASSERTION ERROR

Instead of pipeline ke 20 steps baad obscure error milne ke.

But ek important correction
Aisa mat sochna:
"assert se validation karni hai."
Not exactly.

User/input validation:
if age < 18:
    raise ValueError("Age must be 18 or above")

Internal assumption:
assert age >= 18
Difference:
raise → "Ye input invalid hai."
assert → "Ye condition to already true honi chahiye thi. Agar false hai, mere program/design me problem hai."

Data Engineer example

        raise ValueError("customer_id missing")

Uske baad transformation:

    assert "customer_id" in df.columns    # Ab mujhe confidence hai ki column available hai    ...

Traceback : 

1. What is a Traceback?
A traceback is Python's error report. It shows the sequence of function calls, files, line numbers, and exception information that led to an error.
In simple words: Exception tells you WHAT went wrong; traceback helps you understand WHERE and HOW the program reached that error.
2. Basic Example
def divide(a, b):
    return a / b

result = divide(10, 0)
print(result)
Typical output:
Traceback (most recent call last):
  File "main.py", line 5, in <module>
    result = divide(10, 0)
  File "main.py", line 2, in divide
    return a / b
ZeroDivisionError: division by zero
The final line is the exception type and message: ZeroDivisionError means division by zero occurred.
3. How to Read a Traceback
First look at the LAST line: identify the exception type and error message.
Then locate the failing file and line number.
Then read the call chain upward to understand how execution reached that line.
Do not randomly read the traceback from top to bottom; start with the exception at the bottom and work backward.
4. Understanding the Call Chain
def database():
    return 10 / 0

def process_data():
    return database()

def pipeline():
    return process_data()

pipeline()
pipeline()
    ↓
process_data()
    ↓
database()
    ↓
10 / 0
    ↓
ZeroDivisionError
The traceback records this execution path. This is especially useful when many functions and modules are involved.
5. Traceback vs Exception
Exception = the actual error/problem, for example ZeroDivisionError or KeyError.
Traceback = the execution path showing how the program reached that exception.
Exception → WHAT went wrong
Traceback → WHERE/HOW it went wrong
6. Tracebacks with try-except
try:
    result = 10 / 0
except Exception as e:
    print(e)
This prints only the error message, such as 'division by zero'. It does not show the full traceback.
To print the complete traceback manually:
import traceback

try:
    result = 10 / 0
except Exception:
    traceback.print_exc()
7. The traceback Module
Python provides the built-in traceback module for working with traceback information.
import traceback

try:
    process_data()
except Exception:
    traceback.print_exc()
The most commonly useful function here is traceback.print_exc(), which prints the current exception's traceback.
8. Tracebacks and Logging
In production applications and Data Engineering pipelines, logging is preferred over simple print statements.
import logging

logger = logging.getLogger(__name__)

try:
    process_data()
except Exception:
    logger.exception("Data processing failed")
logger.exception() logs the exception message along with its traceback. This is extremely useful for debugging production ETL jobs.
9. Tracebacks and raise
def transform():
    raise ValueError("Invalid data")

def pipeline():
    transform()

pipeline()
The traceback shows that pipeline() called transform(), and transform() raised ValueError.
10. Re-raising an Exception
If you catch an exception only to pass it upward, use a bare raise inside the except block.
try:
    transform()
except ValueError:
    raise
A bare raise re-raises the currently handled exception and preserves the original traceback context. Do not use raise e when a simple re-raise is all you need.
11. Exception Chaining
try:
    connect_database()
except Exception as e:
    raise RuntimeError("Database connection failed") from e
The 'from e' syntax explicitly records the original exception as the cause of the new exception. This is useful when you want to add a higher-level, meaningful error while preserving the root cause.
12. Data Engineering Example
Imagine a pipeline:
Airflow DAG
    ↓
extract_data()
    ↓
APIClient
    ↓
parse_json()
    ↓
transform_data()
    ↓
load_to_postgres()
If a database error occurs, the traceback can show the path from the DAG to the database function and finally the exact failing line. This helps identify whether the problem is in extraction, transformation, or loading.
13. Example: Data Pipeline Failure
def extract():
    raise ConnectionError("API unavailable")

def transform(data):
    ...

def pipeline():
    data = extract()
    data = transform(data)

try:
    pipeline()
except Exception:
    logger.exception("Pipeline failed")
The traceback will show that pipeline() called extract(), and extract() failed because the API connection was unavailable. This prevents wasting time investigating the transformation stage when extraction is the real problem.
14. Common Exceptions You Will See
ValueError — value has the correct general type but an invalid value.
TypeError — an operation/function received an inappropriate type.
KeyError — a dictionary key or similar key-based lookup does not exist.
IndexError — a list/sequence index is outside its valid range.
FileNotFoundError — a required file does not exist at the specified path.
ZeroDivisionError — division or modulo by zero.
ImportError / ModuleNotFoundError — Python cannot import the requested module/package.
ConnectionError — a connection-related operation failed.
15. Practical Debugging Strategy
1. Read the LAST line.
2. Identify the exception type.
3. Read the error message.
4. Find the last relevant file and line.
5. Inspect the code on that line.
6. Trace upward through the function calls.
7. Check the input/data/state reaching that function.
8. Fix the root cause, not just the final symptom.
This approach is much more reliable than changing random lines until the error disappears.
16. Tracebacks in Data Engineering
ETL/ELT pipelines: identify whether extraction, transformation, or loading failed.
Airflow: identify the task and function that caused a DAG task to fail.
API ingestion: identify the API client/parser line that failed.
Database loading: identify the database operation and the exact failing line.
PySpark jobs: identify the Python-side function or pipeline stage associated with a failure.
Production debugging: combine tracebacks with structured logging to diagnose failures from logs.
17. Important Rules
Always inspect the final exception line first.
Use traceback.print_exc() when you explicitly need to print a traceback.
Use logger.exception() inside an exception handler for production logging.
Use raise to re-raise an exception when you do not need to replace it.
Use 'raise NewError(...) from e' when intentionally wrapping an exception and preserving its cause.
Do not hide exceptions with empty except blocks such as 'except Exception: pass'.
18. Interview Definition
A traceback is Python's report of the call stack that shows the sequence of function calls, file names, line numbers, and exception information that led to an error.
19. Quick Revision
Exception  → WHAT went wrong
Traceback  → WHERE/HOW the program reached the error
raise      → explicitly raise an exception
try/except → handle an exception
traceback.print_exc() → print the current traceback
logger.exception()    → log the exception with traceback
raise                  → re-raise while preserving the current exception context
